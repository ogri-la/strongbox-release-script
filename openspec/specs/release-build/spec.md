# release-build Specification

## Purpose

Produces every release artefact and every per-release repository update locally, verifies them, and records what went into them, all without credentials or remote side effects, so that a later publish only transmits what has already been checked.

## Requirements

### Requirement: Build has no remote side effects
`./release.sh build <version>` SHALL NOT push, tag, upload or open anything on any remote. It SHALL run without any credential available to its stages.

#### Scenario: Build succeeds
- **WHEN** `./release.sh build 7.8.0` completes
- **THEN** no tag `7.8.0` in this repository or strongbox, GitHub release, AUR commit or Flathub branch was created remotely

#### Scenario: Build fails partway
- **WHEN** the AppImage step fails
- **THEN** the pipeline exits non-zero, and the remotes are in the same state as before the run

### Requirement: Source is consistent with the version
Build SHALL check out strongbox `master` and record the commit SHA it builds from. Before building, it SHALL verify that:
- `project.clj` declares exactly `<version>`.
- `CHANGELOG.md` has a section for `<version>`.
- A remote tag `<version>` either does not exist or points at the recorded commit.

#### Scenario: PR not yet merged
- **WHEN** `master`'s `project.clj` still declares the previous version
- **THEN** the build stops before compiling, stating the version mismatch

#### Scenario: Tag exists on another commit
- **WHEN** the remote tag `7.8.0` points at a commit other than `master`'s HEAD
- **THEN** the build stops, reporting both commits

### Requirement: Artefacts are produced
Build SHALL produce, in the release's workspace:
- `strongbox-<version>-standalone.jar`
- `strongbox-<version>-x86_64.AppImage`, containing a JRE created with `jlink` from the pinned JDK 17
- a `.sha256` file for each, in `sha256sum` format

#### Scenario: Artefacts present
- **WHEN** the build succeeds for `7.8.0`
- **THEN** the four files exist, and each `.sha256` file verifies with `sha256sum --check`

### Requirement: glibc floor is enforced
Build SHALL compute the highest `GLIBC_` symbol version required by every ELF shared object in the AppImage, including those packed inside the bundled jar. It SHALL fail if that version is above the configured ceiling. The initial ceiling is `2.27`.

#### Scenario: Within ceiling
- **WHEN** the highest required symbol across the JRE and JavaFX natives is `GLIBC_2.17`
- **THEN** the check passes and records `2.17` as the floor

#### Scenario: JavaFX upgrade raises floor
- **WHEN** a native library inside the jar requires `GLIBC_2.34`
- **THEN** the build fails, naming the library and the symbol version

### Requirement: AppImage runs on the oldest supported system
Build SHALL run the AppImage's bundled JRE inside a container whose glibc equals the configured ceiling, and SHALL fail if the JRE does not start.

#### Scenario: JRE starts on an old system
- **WHEN** the extracted AppImage's `java -version` is run in the ceiling-glibc container
- **THEN** it exits zero and prints the pinned JDK version

### Requirement: Per-release repository updates are derived locally
Build SHALL prepare, as local unpushed commits in fresh clones, copies of the rendered files in `dist/`:
- **AUR:** the `strongbox` package with the rendered `PKGBUILD`, `changelog` and `strongbox.desktop`, and `.SRCINFO` regenerated by `makepkg --printsrcinfo` in an Arch Linux container. The regenerated `.SRCINFO` SHALL be written back to `dist/`.
- **Flathub:** a branch `<version>` in a clone of `flathub/la.ogri.strongbox`, carrying the rendered `la.ogri.strongbox.yml`. The manifest SHALL fetch `metainfo.xml`, `strongbox.desktop` and `strongbox.svg` from `dist/flatpak/` at this repository's tag `<version>`, with sha256 values computed from those rendered files. Flathub requires metadata files to come from upstream rather than be copied into its repository.
- **GitHub release notes:** the `<version>` section extracted from `CHANGELOG.md`, rendered into `dist/`.

Each downstream clone SHALL contain only files from `dist/`. Files that cannot be derived SHALL NOT be stored in a downstream repository.

#### Scenario: Derived commits exist locally
- **WHEN** the build succeeds
- **THEN** each of the two clones has exactly one new local commit, and `git status` reports it ahead of its remote by one

#### Scenario: Downstream holds only rendered files
- **WHEN** the build succeeds
- **THEN** the files in each downstream clone, excluding `.git`, are exactly the files in that target's directory in `dist/`, byte for byte

#### Scenario: Checksums agree
- **WHEN** the build succeeds
- **THEN** the AppImage checksum in `PKGBUILD` and the jar checksum in `la.ogri.strongbox.yml` equal the checksums in the local `.sha256` files, and each metadata checksum in `la.ogri.strongbox.yml` equals the sha256 of the file of that name in `dist/flatpak/`

### Requirement: AUR package builds locally
Build SHALL run `makepkg` for the prepared AUR package in an Arch Linux container with no network. The AppImage is supplied from the local build, not downloaded.

#### Scenario: Package builds
- **WHEN** `makepkg` runs with the local AppImage in place
- **THEN** it produces a `strongbox-<version>-1-x86_64.pkg.tar.zst` and exits zero

#### Scenario: Checksum mismatch
- **WHEN** the `PKGBUILD` checksum does not match the local AppImage
- **THEN** the build fails before any publish is possible

### Requirement: Flatpak metadata is valid
Build SHALL validate the rendered `metainfo.xml` with `appstreamcli validate` and SHALL fail on errors. Warnings SHALL be shown but SHALL NOT fail the build.

#### Scenario: Invalid metainfo
- **WHEN** a changelog entry produces markup that is invalid in metainfo
- **THEN** the build fails, showing the validator's error

### Requirement: Build is recorded
Build SHALL write a machine-readable build record to `dist/`. It SHALL hold: the version, the strongbox commit SHA, this repository's commit SHA and whether its working tree had changes outside `dist/`, the image digests, the JDK version, the SHA-256 of the downloaded catalogue, the SHA-256 of each artefact, the measured glibc floor, and the local commit SHA of each derived repository update. The record SHALL be validated against a schema when written and when read.

#### Scenario: Record written
- **WHEN** the build succeeds
- **THEN** the record exists in `dist/`, validates against its schema, and its artefact checksums match the files

#### Scenario: Build fails
- **WHEN** any build step fails
- **THEN** `dist/` is unchanged, because rendered files and the record replace `dist/` only when every build step has succeeded

### Requirement: Release files are rendered from templates
Build SHALL render every per-release packaging file from templates in this repository, using one render context. The context SHALL hold the version, the artefact checksums and the text derived from strongbox's changelog. Rendered files SHALL be written to `dist/`, one directory per target, with every value written out in full. `dist/` SHALL be replaced only when every build step has succeeded. Rendering SHALL fail if a template uses a name that is not in the context. It SHALL also fail if a context value is used by no template. The context SHALL be written to `dist/` beside the files rendered from it.

#### Scenario: Rendered files
- **WHEN** the build for `7.8.0` succeeds
- **THEN** `dist/` holds the AUR files (`PKGBUILD`, `.SRCINFO`, `changelog`, `strongbox.desktop`), the Flathub manifest (`la.ogri.strongbox.yml`), the Flatpak metadata (`metainfo.xml`, `strongbox.desktop`, `strongbox.svg`), the AppImage's `strongbox.desktop`, the release notes and the render context, and no rendered file contains a template placeholder

#### Scenario: Unknown name in a template
- **WHEN** a template refers to `{{ jar_sha512 }}` and the context has no such name
- **THEN** the build fails, naming the template and the unknown name, and `dist/` is unchanged

#### Scenario: Version given once
- **WHEN** `./release.sh build 7.8.0` is run
- **THEN** `7.8.0` is the only version given by hand, and every version, URL and checksum in `dist/` is derived from it or from the build

### Requirement: Downstream drift is detected
Before rendering, build SHALL compare the files in each downstream repository with the committed files in `dist/` for that target, which are the files last pushed. If they differ, the downstream copy was edited outside this repository. Build SHALL then fail, showing the difference per file. It SHALL tell the user to move the edit into a template, then run `./release.sh adopt <target>`. `adopt` SHALL copy the downstream files into `dist/<target>` for the user to review and commit, and SHALL change nothing remote.

#### Scenario: No drift
- **WHEN** the Flathub and AUR repositories hold exactly the committed files in `dist/flathub` and `dist/aur`
- **THEN** the drift check passes

#### Scenario: Downstream edited
- **WHEN** a Flathub contributor changed `runtime-version` from `24.08` to `25.08` in `flathub/la.ogri.strongbox`
- **THEN** the build fails before rendering, showing the `runtime-version` line as a difference in `la.ogri.strongbox.yml`, and naming `./release.sh adopt flathub`

#### Scenario: Edit adopted
- **WHEN** the manifest template is changed to `25.08`, `./release.sh adopt flathub` is run, the result is committed, and the build is run again
- **THEN** the drift check passes, and the rendered manifest says `25.08`

#### Scenario: Adopt shows the edit
- **WHEN** `./release.sh adopt flathub` is run
- **THEN** `dist/flathub` holds the downstream files, and `git diff dist/flathub` shows exactly the downstream edits

### Requirement: Packaging is linted with Flathub's linter
Build SHALL run Flathub's `flatpak-builder-lint` on the rendered manifest, with Flathub's per-app exceptions applied, and on the rendered `metainfo.xml`. For the manifest, errors SHALL fail the build, and warnings SHALL be shown without failing it. For the metainfo, build SHALL keep the linter's own behaviour, which Flathub's buildbot also applies: warnings fail, and every URL in the metainfo must resolve. Every URL in the rendered metainfo SHALL therefore exist before the release is published.

#### Scenario: Linter error
- **WHEN** the rendered metainfo lacks an element that Flathub requires
- **THEN** the build fails, showing the linter's error

#### Scenario: Runtime update available
- **WHEN** the linter warns that a newer Flatpak runtime is available
- **THEN** the build succeeds, and the warning is shown

#### Scenario: Unreachable screenshot
- **WHEN** a screenshot URL in the rendered metainfo does not resolve
- **THEN** the build fails, naming the URL

#### Scenario: Screenshots before the release tag exists
- **WHEN** `7.8.0` is built and strongbox has no tag `7.8.0` yet
- **THEN** the metainfo check passes, because screenshots are referenced at the strongbox commit being built
